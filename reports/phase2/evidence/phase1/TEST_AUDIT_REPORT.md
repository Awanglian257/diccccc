## 6. Bug 清单、位置与复现

严重程度定义：P0 为系统性不可用/重大安全或不可逆损失；P1 为核心结果明显错误，可能误导健康决策；P2 为重要校验、状态或一致性缺陷；P3 为边界规范、工具链或低影响问题。以下文件位置均相对于主审查交付目录，行号对应本次快照。

### B01 / P2：负数食物重量被静默转为零并保存

- 位置：`index.html:5383` `comboItemNutrition()`；`:5435` `addComboToDiary()`。
- 复现：打开组合餐；加入米饭，数量 -100、单位 g；点击“记入这一天”。
- 实际：输入框 checkValidity=false，但按钮路径未阻止提交；保存数量 0、热量 0 的记录，并被视为营养完整。
- 预期：明确拒绝非法值，保持数据不变；不要静默把非法输入变成真实记录。
- 证据：A03。建议统一业务校验，不能仅依赖 input 属性。

### B02 / P2：组合餐没有合理数值上限

- 位置：`index.html:5383` `comboItemNutrition()`、`:5410` `computeCombo()`、`:5435` `addComboToDiary()`。
- 复现：米饭数量输入 1000000000000 g，提交。
- 实际：保存 1,160,000,000,000 kcal，统计 complete=true。
- 预期：设置业务上限并拒绝明显不合理值，汇总不能接受该记录为完整数据。
- 证据：A04。建议校验有限数、范围、汇总上限，并在持久化前复验。

### B03 / P1：不同份量单位使用相同克重

- 位置：`index.html:5383` `comboItemNutrition()`，非 g 分支直接使用 PORTIONS[f.id].g。
- 复现：米饭数量 1，分别选择“勺”和“碗”，比较计算结果；A05 在浏览器内直接调用同一计算函数核对。
- 实际：两者均 150 g、174 kcal；代码没有按所选单位查换算关系。
- 预期：仅使用该食物与指定单位的对应换算；没有换算依据时提示输入克重。不能把任意单位等同默认份量。
- 影响：常见录入即可产生错误营养值，并进入完整统计。
- 证据：A05。

### B04 / P2：组合餐连续点击造成重复实际摄入

- 位置：`index.html:5435` `addComboToDiary()`、`:5317` `pushEntry()`。
- 复现：填写同一份米饭 100 g 组合餐，连续点击两次记入按钮，不改变表单。
- 实际：产生两条相同实际餐食，热量从 116 变为 232 kcal。
- 预期：同次提交防重；如用户确实要吃第二份，应有明确再次录入行为。
- 证据：A06。建议提交令牌/防重及成功后重置状态，不能仅按食物名称永久去重。

### B05 / P3：组合餐与快记日期允许范围不同

- 位置：`index.html:5435` `addComboToDiary()`；对照 `:7323` `editQuickMeal()`。
- 复现：组合餐选择 1899-01-01 保存；对照快记的 1900–2200 校验。
- 实际：组合餐接受该日期，快记按另一范围拒绝。
- 预期：各入口统一日期策略。
- 证据：A07。注意：1899-01-01 本身不是非法日历日期；此项不能宣称已证明数据损坏。建议先确定统一业务范围。

### B06 / P1：修改餐食后沿用旧食物的宏量营养

- 位置：`index.html:7323` `editQuickMeal()`，保存时复制原 entry 后只更新部分字段。
- 复现：准备鸡胸肉记录（100 g、165 kcal、蛋白 31 g、脂肪 3.6 g、foodId=chicken）；从今日记录展开该餐编辑，将名称改为披萨、热量改为 800，保存。
- 实际：名称披萨、热量 800，但 p=31、f=3.6、c=0、foodId=chicken、grams=100 继续保留；每日统计 complete=true。
- 预期：更换食物或仅更改热量时重新解析/计算，或清除不再可信的宏量营养并标为待补。
- 证据：A09，使用隔离存储准备原始条目后执行真实编辑界面。

### B07 / P2：删除校准依据后旧 TDEE 仍被视为有效

- 位置：`index.html:3322` `calibrationFresh()`、`:3339` `effectiveTDEE()`、`:3454` `recalibrateTDEE()`。
- 复现：准备 12 天完整摄入（每日 2100 kcal）和跨度 15 天的 6 个体重点；强制校准得到 2151 kcal；在界面删除其中一天全部饮食；再次检查反推与有效 TDEE。
- 实际：反推提示仅剩 11 天、不满足要求，但 effectiveTDEE 仍返回 source=calibrated、2151、stale=false。
- 预期：删除或修正依据后校准应失效/明确标记为旧估计，不能继续声称其证据满足要求。
- 证据：A13。现有新鲜度主要看年龄、档案和体重，缺少记录版本指纹。保留旧估计作参考与将其标成当前有效需区分。

### B08 / P2：重新保存相同基准重置阶段开始日期

- 位置：`index.html:3189` `saveProfile()`，无条件使用 todayStr() 设置 start；保存基准路径调用该函数。
- 复现：准备开始于 2026-07-24 且已经推进的计划；以相同输入执行 saveProfile(buildPlan(p.inp))。
- 实际：start 改为 2026-11-21，日期阶段索引从 1 退到 0。
- 预期：普通保存保留起点；重新开始计划应是明确操作。
- 证据：A20，浏览器内函数探针；该用例无近期体重，走日期推进路径。若设计意图为每次重新计算都重启，应在界面明确说明并取得相应选择。

### B09 / P3：干净交付包的评估命令失败

- 位置：`tests/evaluate.cjs:14`，顶层评估流程直接 fs.writeFileSync 写 docs/evaluation-results.json。
- 复现：将交付包放入干净目录，在没有 docs 子目录的情况下执行 npm run evaluate。
- 实际：进程退出码 1，ENOENT；先运行浏览器测试创建 docs 后，同一命令退出码 0。
- 预期：评估脚本自行创建输出目录，命令不依赖测试执行顺序。
- 证据：pristine-evaluate-command.json 与 evaluate-command.json。未对源码作修复。
